### Recently released
- `opus-forge-glyph-occlusion` (2026-05-19) — surgical fix for John's "symbols are going over highlighted nodes' circles, no hierarchy coherent" report. Root cause: glyphs are DOM SVG spans positioned over the canvas. Canvas-side disks have proper z-layering (selected z=0 wins over neighbor z=0.3/0.6 via depth test), but DOM glyphs sit on top of the entire canvas regardless of which canvas-side disk they geometrically overlap — so a focused-neighbor's glyph visually paints over the selected node's glow halo. **Surgical fix shipped here**: `syncGlyphFocus` now computes an OCCLUSION ZONE (screen circle = `n.r * scale * glow_extent`) around each SELECTED node; any non-selected glyph whose screen center falls inside any occlusion zone gets `opacity: 0`, so the selected halo stays visually uncluttered. Also wired `syncGlyphFocus` into `camera.onChange` so occlusion updates live as the user pans/zooms past selected nodes. **Deferred (architectural)**: move glyphs into the WebGPU canvas (texture atlas of 17 glyph SVGs + per-instance shader pass with same z-layering as disks). The right long-term fix — glyphs would participate in the same depth pipeline as disks, no DOM/canvas seam — but ~2hr batch by itself. Cache-bust `20260519-glyph-occlusion`. Files: `src/js/views/forge.js`, `index.html`.
- `opus-forge-glow-glyph-fix` (2026-05-19) — two follow-up polish fixes for the items deferred from `03e1589`. **(1) Selected-node glow clipping square** — vertex shader now uses `quad_scale = v.selected_glow.w * 1.5` (was equal to `selected_glow.w`). The fragment shader's smoothstep still has the same `(1.0, glow_outer)` falloff range, but the QUAD now extends 1.5× past `glow_outer`. Pixels beyond the smoothstep range return `glow_fade = 0`, `final_a < 0.08` discard threshold (bumped from 0.04), no depth write — adjacent disk quads paint cleanly through where the selected node's glow has fully dissipated. The visible square outline around selected-node glows is gone; falloff is perfectly circular. **(2) Glyph z-order by state** — `syncGlyphFocus` now sets `z-index: 3 / 2 / 1` per glyph based on `selectedSet` / `focusedSet` / dim. A selected node's glyph always paints on top of its neighbors' glyphs (was DOM-order-dependent and could be buried). Files: `src/js/engine/renderer/webgpu.js`, `src/js/views/forge.js`, `index.html` (cache-bust `20260519-glow-glyph-fix`).
- `opus-forge-resize-snap-fix` (2026-05-19) — found the real cause of John's "wheel snaps and centers ~1 second after resize" report. **Root cause**: `src/js/app.js:10267` has a window.resize handler that debounces 200ms then calls `setView(STATE.view)` — for Forge that means a full teardown + re-mount via `VIEWS.forge.render()` → engine destroyed → fresh `setup()` → `resizeAndFit(true)` → fitToExtent. Forge has its own ResizeObserver that already handles canvas resize without a re-mount; the global app.js handler is for views that read clientWidth at mount and don't have their own observer. Fix: app.js window.resize handler now short-circuits if `STATE.view === 'forge'`. Also added **camera pan bounds**: new `camera.setPanBounds(x0, y0, x1, y1)` API; view layer calls it after every `fitToExtent` with a half-worldSpan margin so the user can pan a half-viewport beyond each edge but not infinite-pan into empty space. Camera `panByScreen` + `tick` both clamp the center. Files: `src/js/app.js` (forge skip in resize handler), `src/js/engine/camera.js` (pan bounds API), `src/js/views/forge.js` (calls setPanBounds after fitToExtent), `index.html` (cache-bust `20260519-resize-snap-fix`).
