# Forge robustness audit 03 — lifecycle invariants + order-of-ops

**Filed:** 2026-05-20
**Filed by:** Lane-B audit goblin (read-only)
**Scope:** Map every invariant assumed by the Forge view's lifecycle (mount / resize / mode-switch / view-switch / disposal) and surface every hostile sequence that can violate one.
**Reads-with:**
- `AUDIT/forge-edge-state-invariant-2026-05-18.md` (the "FINAL DIAGNOSIS" addendum is the canonical drift-on-remount story)
- `AUDIT/forge-animation-pipeline-2026-05-20.md` (current animation pipeline state)
- `AUDIT/forge-glyph-migration-handoff-2026-05-20.md` (GPU glyph pipeline current state)
**Not in scope:** correctness of the GPU shaders themselves; content of the dev panel.

This audit is a snapshot of `src/js/views/forge.js@bfc35d2`, `src/js/engine/renderer/webgpu.js@bfc35d2`, `src/js/engine/camera.js@bfc35d2`, and the Forge mount path in `src/js/app.js@bfc35d2`.

---

## 1. TL;DR — top 3 invariant violations

1. 🔴 **Renderer disposal leaks the glyph atlas texture, the glyph instance VBO, the swap-chain texture, and the `bucketPalette` Float32Array.** `webgpu.js destroy()` does not call `atlasTex.destroy()` nor `glyphInstanceVbo.destroy()`. Forge↔other view ping-pong leaks ~ atlas_w·atlas_h·4 bytes + ~21 KB instance buffer per mount, and the `device.destroy()` race-condition window (described below) can leave the swap-chain partially configured.
2. 🔴 **`resizeAndFit` blindly runs `rebakeNodes` + `rebakeEdges` + `recomputeFocus` even if the atlas / renderer / first mount-time pack hasn't completed.** The atlas-build promise can resolve AFTER `resizeAndFit(initial=true)` has already fired; the bootstrap is `await gpu.create → setBucketPalette → buildAtlas.then(…) → resizeAndFit(true) → rebuildForMode(…) → resizeObs.observe(stage)`. If a `ResizeObserver` fires DURING the atlas-build window, `rebuildGlyphInstanceBuffer` runs with `local.glyphAtlas === null` and returns silently — but **the disk + edge pipeline still draws**, so the user sees disks with no glyphs for one resize cycle. A second resize will refresh, but the asymmetry is real.
3. 🟡 **`camera.onChange` does heavy work (`rebakeNodes` → `rebakeEdges`) on a 5%-drift trigger that fires during `fitToExtent` from `resizeAndFit(initial=true)` AND from `rebuildForMode`.** `fitToExtent` emits `_emit()`, the onChange listener sees ratio > 1.05, fires `rebakeNodes()`, which calls `packNodes` — which reads `camera.state.scale` — which has just been set to the fit scale. This currently works because `local.packedAtScale` is initialized via `rebakeNodes` itself, but mode-switch fires `camera.fitToExtent` BEFORE `packNodes` runs, so `local.packedAtScale` is stale from the previous mode. Net effect today is benign double-pack on mode switch; net effect after any "skip pack if packedAtScale === currentScale" optimisation would be a stale-radius bug.

## 3. Hostile-sequence matrix

Each row is a pair of transitions that can interleave on a real browser. Columns: what the second event sees / breaks.

| Sequence | What can break | Severity |
|---|---|---|
| **glyph-atlas-resolve × first resize** | Atlas promise resolves AFTER `bootstrap` already fired `resizeAndFit(initial=true)` + `rebuildForMode`. If a `ResizeObserver` fires in that window (window resize during initial paint), `rebuildGlyphInstanceBuffer` runs with `local.glyphAtlas === null` → early-return → user sees disks with no glyphs until the next `rebuildGlyphInstanceBuffer` call (atlas-resolve handler calls it once on success, so resolves itself within a frame — but the order is undefined). | 🟡 |
| **`resize` × `pointermove` (hover-in-flight)** | `ResizeObserver` fires → `resizeAndFit(false)` → `rebakeNodes` mutates `local.mode.hitNodes` / `hitById` MID-RAF. The `pointermove` handler may have just called `hitTestAt(...)` against the OLD `hitNodes` array (captured at handler entry by closure of `local.mode.hitNodes`). Actually `hitTestAt` reads `local.mode.hitNodes` per call, so it re-resolves through `local.mode` — but the in-flight `recomputeFocus` (rAF-scheduled by `setHoverId`) reads `local.mode.nodePacked.idIndex` which is also being replaced. **rAF-ordering accident:** if `recomputeFocus` runs AFTER `rebakeNodes` (same frame), it reads the new idIndex, allocates new `nodeTargets` of the right length, no problem. If `recomputeFocus` runs BEFORE, it allocates new `nodeTargets` of the OLD length, then `rebakeNodes` immediately replaces `nodeTargets` again (different length), and `nodeStates` gets re-allocated with the new length — every in-flight fade snaps. | 🟡 |
| **`resize` × `recomputeFocus` (locked-hover in flight)** | `resizeAndFit(false)` calls `rebakeNodes → rebakeEdges → recomputeFocus → forceWriteEdgeState → drawFrame`. If the user was mid-hover (pending `_hoverRafId`), the pending rAF callback fires AFTER `resizeAndFit` completes; it calls `recomputeFocus` again, harmlessly. **But** `_hoverPendingId` may now point at an id that survived the mode (deities → deities, same hover) — fine. **If** the resize fires during a mode-switch (`rebuildForMode` mid-execution), the rAF-scheduled `recomputeFocus` sees a half-built `local.mode`. Not currently triggerable because `rebuildForMode` is synchronous, but a future async refactor would expose this. | 🟢 (latent) |
| **`mode-switch` × `lockedSet`** | `rebuildForMode` resets `local.lockedSet = new Set()` and `local.focusedSet = null`. **The HUD's lock-count display is reset to '—'.** But the dev panel does not observe `lockedSet`; if a UI ever subscribed to lock state it would silently desync. Today benign. The deeper issue: **`local.lockedSet` Set instance is replaced**, so any code that held a reference to the OLD lockedSet still holds the old set. `recomputeFocus` reads `local.lockedSet` each call so this is fine. **If** any closure ever captured `lockedSet` by reference at mount time, it would leak. | 🟢 |
| **`mode-switch` × `_hoverRafId` pending** | `rebuildForMode` does NOT cancel `_hoverRafId`. The pending rAF callback fires after `rebuildForMode` completes, calls `recomputeFocus` with `_hoverPendingId` from the OLD mode. `_hoverPendingId` is a node id that may not exist in the new mode. `recomputeFocus` calls `graph.focusedSetFor(local.hoverId, lockedSet, adjacency)`. Adjacency is now the new mode's; the old id isn't a key → `focusedSet` returns the empty set or just the orphan id (depending on `focusedSetFor` semantics — see `graph/adjacency.js`). Result: a stray "hover" on a node that doesn't exist, briefly. Auto-clears on the next real pointermove. | 🟡 |
| **`mode-switch` × in-flight fade** | `rebuildForMode` allocates `local.nodeStates = new Float32Array(N*2)` (FRESH), `local.nodeTargets = new Float32Array(N*2)`. The previous fade buffers are GC'd. This is `wholesale-replace` per the animation-pipeline audit's invariant #1 — but it's correct here because the instance counts differ across modes. **The hidden cost:** the animation-pipeline audit's invariant says "Never wholesale-replace `local.nodeStates`" — `rebuildForMode` is an explicit exception, but no comment marks it. A future refactor that tries to "fade-aware-ify" `rebuildForMode` (mirroring `rebakeNodes`) would BREAK on cross-mode hover because the buffer sizes differ. The exception needs a written note. | 🟢 (documentation gap) |
| **`mode-switch` × dev-panel slider drag** | `rebuildForMode` does NOT freeze `local.params`. If the user is dragging a slider during a mode-switch, `setParam` fires concurrently with `rebuildForMode`. `setParam` routes based on `name`; some routes call `rebakeNodes/rebakeEdges` which use `local.mode.*`. Race: if `setParam('node_radius_tier1', …)` lands BETWEEN `rebuildForMode`'s `packNodes` and its `drawFrame`, the new tier-radius is read by neither the just-completed pack nor the just-completed draw — it's queued for the NEXT pack. Eventually consistent, but a flicker is possible. **Not currently observed** because mode-switch UI blocks the dev panel visually; could appear when a future keyboard shortcut switches modes. | 🟢 |
| **`view-switch` (Forge → Pantheon → Forge) × dev-panel state** | `setView('pantheon')` → `app.js` calls `el._engine.destroy()` → renderer torn down. New `setView('forge')` → creates new pane → `window._forge.render(pane)` → new `local`, new camera, new renderer. **The dev-panel's `state.params` survives** (it's module-scope in `dev-panel-forge.js`). Option B in `render()` reads `window.AtlasEngineForgeDevPanel.getState()` and seeds `local.params` from it — so user-tuned params persist across the view-switch. ✅ Working as designed. **However:** `_hoverRafId` is closure-local to the OLD render() call; the OLD render's pending rAF will fire AFTER teardown begins, see `local.destroyed === true`, and bail. ✅ Safe. **But:** the OLD render's `_forgeDebug` is overwritten by the NEW render's assignment (`window._forgeDebug = { … }`). Bug: any tooling that grabbed a reference to the old `_forgeDebug` (a console-stored variable, for example) now holds a stale object whose closures reference the destroyed renderer. Calling its methods would throw or return garbage. Low-priority but real. | 🟢 |
| **`view-switch` × glyph atlas in flight** | Atlas build is `Promise<atlas>`. If user switches AWAY from Forge before atlas resolves: the `.then` handler still runs, checks `local.destroyed || !local.renderer` → bails. ✅ Safe. **But:** the atlas's underlying Canvas2D + ImageBitmap (likely allocated in `glyphmod.buildAtlas`) is not explicitly released; relies on GC. Low priority, but if Forge is mounted/unmounted in a tight loop, atlas builds pile up. | 🟢 |
| **`fitToExtent` (from `rebuildForMode`) × `camera.onChange` 5%-drift** | `camera.fitToExtent` calls `_emit()`. The listener computes `ratio = camScale / lastScale`. On the first ever call `lastScale = local.packedAtScale || camScale = undefined || camScale = camScale`, so `ratio === 1`. No re-pack. **But on a mode-switch:** `rebuildForMode` calls `camera.fitToExtent` BEFORE the new `packNodes`; the listener sees the new scale, compares against `local.packedAtScale` which is still the OLD mode's scale. If the ratio is > 5%, the listener fires `rebakeNodes()` which packs `local.mode.nodes` — but `local.mode` STILL points at the old mode (replacement happens after this listener fires). Result: a "lost" pack of the OLD mode at the NEW scale, immediately discarded by `rebuildForMode`'s own pack. **Not user-visible today** (it's wasted work, not wrong work), but it's the textbook order-of-ops fragility that has bitten this file before. | 🟡 |
| **`pointerdown` (drag start) × in-flight `flyTo`** | `pointerdown` calls `camera.stopAnim()` (kills `flyToAnim`, `panAnim`, `zoomAnim`). ✅ Safe. The animation loop notices `!stillMoving && !stillFading` on its next tick and exits. | ✅ |
| **`wheel` × `wheel` × `wheel` (rapid)** | `nudgeZoomTarget` compounds against existing `zoomAnim.targetScale`. ✅ Designed. But: every wheel event also calls `hitTestAt + setHoverId` synchronously. With rapid wheel events the hit-test runs N times per second, each doing an O(N) iteration of `hitNodes`. At 60 Hz on a 663-node mode that's 40k distance checks per second. Not catastrophic, but not great. Could coalesce with the same rAF pattern `setHoverId` already uses for `recomputeFocus`. | 🟢 |
| **`pointermove` (drag) × `panByScreen` × `camera.onChange` 5%-drift** | Each `panByScreen` emits `_emit()`. `onChange` listener computes `ratio = camScale / lastScale`. **Pan doesn't change scale**, so ratio === 1 → no rebake → just `drawFrame`. ✅ Safe. | ✅ |
| **`destroy()` × pending `_hoverRafId`** | `_engine.destroy` cancels `local.animRafId` but does NOT cancel `_hoverRafId`. The pending rAF fires, checks `local.destroyed`, bails. ✅ Safe. **But** if a future change forgets the `if (local.destroyed) return;` guard inside the rAF callback (which is a 1-liner easy to miss in a refactor), a use-after-destroy would surface. Defence in depth would have `destroy()` cancel `_hoverRafId` and `local.idleLabelRaf` explicitly. | 🟡 |
| **`destroy()` × renderer GPU work still in queue** | `renderer.destroy()` calls `device.destroy()`. If `drawFrame` had just submitted a command buffer that hasn't finished GPU-side, `device.destroy()` invalidates the swap-chain texture mid-frame. WebGPU spec says it should be safe (texture refs are valid until end of frame), but Safari and Firefox Nightly have historically shown sporadic console errors here. Currently unobserved on Chrome. | 🟢 |
| **`device.destroy()` × glyph atlas texture** | `renderer.destroy()` does NOT call `atlasTex.destroy()` before `device.destroy()`. WebGPU spec: `device.destroy()` destroys all its child objects, so the atlas IS released — but the explicit `atlasTex.destroy()` is missing from the destroy list. Same for `glyphInstanceVbo` and `glyphUvUbo`. Today benign because device-destroy is a hammer, BUT: if anyone ever changes Forge to keep the device alive across view-switches (a reasonable perf win), this becomes a leak. | 🔴 (latent — explicit cleanup missing) |
| **`fitToExtent` × pan bounds** | `rebuildForMode` calls `camera.fitToExtent` then `camera.setPanBounds`. `fitToExtent` writes `state.centerX/centerY/scale` and clears all anims. `setPanBounds` calls `clampCenter` which clamps the JUST-WRITTEN center to the bounds. ✅ Safe ordering. **But** if the order were reversed (a future refactor that sets pan bounds first), `clampCenter` would clamp the OLD center to the new bounds, then `fitToExtent` overwrites center anyway — harmless. The inverse (`setPanBounds` after `fitToExtent`) is correct and intentional. | ✅ |
| **resize × depth-texture stale** | `renderer.resize(w, h)` reconfigures the swap-chain but does NOT clear `depthTex`. The next `drawFrame` calls `ensureDepthTex(canvas.width, canvas.height)` which checks `depthTexW === fbW && depthTexH === fbH` — mismatch → destroys old, allocates new. ✅ Self-healing. **But** this re-allocation happens MID-DRAW (inside drawFrame), so the first frame after a resize pays the GPU-resource-allocation cost on the render thread. Not a correctness bug; a 1–2 ms hiccup on resize. | 🟢 |
| **`recomputeFocus` × stale `nodesById`** | `recomputeFocus` reads `local.mode.nodesById`. `rebuildForMode` rebuilds it; `rebakeNodes` does NOT touch it (it rebuilds `hitNodes`/`hitById` but leaves `nodesById` alone). `nodesById` is keyed by `n.id` referencing the SAME node objects from `vault.nodes` — so a rebake doesn't invalidate it. ✅ Safe. **But** if a future content reload (`VAULT_DATA` swap) happens without a `rebuildForMode`, `nodesById` would point at orphaned node objects. Today Forge doesn't reload vault data — but a "hot reload" feature would expose this. | 🟢 (latent) |
| **scrubber-drag × rAF coalescing** | `onPointerMove` (scrubber) calls `recomputeFocus()` synchronously on every move. At 120 Hz this is the same un-coalesced anti-pattern that the audit found in hover before commit `98bc609`. The scrubber should rAF-coalesce too. (Animation-pipeline audit §6/A is the precedent.) | 🟡 |
| **mode-switch × scrubber state** | `rebuildForMode` does NOT clear `local.timeline`. The timeline state persists across modes — which is right (user wants to keep their date filter on mode-switch). **But:** `wireTimelineScrubber()` only runs ONCE in `bootstrap()`, NOT in `rebuildForMode`. The IN/OUT bounds derived from the FIRST mode's date range freeze. If the user switches deities → documents (which has wildly different date span), the slider's date range is wrong for the new mode. Same lo/hi mapping; UI displays stale year boundaries. **`recomputeFocus`'s overlap check still works** (it compares per-node dates against `tl.inDate/outDate`), so the FILTER is correct — but the slider's visible bounds are misleading. | 🟡 |
| **dev-panel `setIcon` × glyph atlas** | `setIcon(nodeType, iconId)` mutates `local.iconByType` and calls `rebakeGlyphsForMode` → `rebuildGlyphInstanceBuffer`. **But** `rebuildGlyphInstanceBuffer` does NOT read `local.iconByType` (per the glyph-migration handoff's "What's NOT yet done" list). So the icon-override is silently ignored. Documented gap; not new. | 🟢 (documented) |

## 4. Findings list, severity-ranked

### 🔴 CRITICAL

- **F1. Renderer destroy() leaks `atlasTex`, `glyphInstanceVbo`, `glyphUvUbo`, and the glyph bind group.** `webgpu.js:1156-1167` lists `quadVbo, edgeRibbonVbo, diskUbo, viewUbo, nodeInstanceVbo, edgeInstanceVbo, nodeStateVbo, edgeStateVbo, depthTex` — atlas resources are not enumerated. Current safety net is `device.destroy()` which is supposed to release everything; **but** the audit's job is to surface latent invariants. The moment Forge ever holds the device across view-switches, this list becomes a leak. Symptom: GPU memory monotonically grows on Forge re-mounts.

- **F2. `_engine.destroy()` does not cancel `_hoverRafId` or `local.idleLabelRaf`.** Today saved by the `if (local.destroyed) return` guards inside the rAF callbacks. A single missed guard in a future refactor produces a use-after-destroy on stale `local.mode`. Defensive cancellation is one line each.

### 🟡 IMPORTANT

- **F3. `rebuildForMode` does not cancel `_hoverRafId`.** Pending rAF callback fires AFTER the mode has changed, calling `recomputeFocus` with an old-mode hover id against the new mode's adjacency. Tiny brief "ghost hover" possible. Should cancel-and-clear.

- **F4. `camera.fitToExtent` emit from `rebuildForMode` can trigger `camera.onChange`'s 5%-drift `rebakeNodes` on the OLD mode** before `rebuildForMode` replaces `local.mode`. Wasted work today; will become a stale-radius bug the moment anyone optimises the listener to skip on `packedAtScale` equality. Race window is microseconds but real.

- **F5. `wireTimelineScrubber()` is bootstrap-only.** Mode-switch leaves the slider bounds frozen at the first mode's date span. Filter math still works but UI is misleading. The slider should re-derive bounds inside `rebuildForMode`, or expose a `refreshScrubberBounds()` hook called from there.

- **F6. Scrubber drag fires `recomputeFocus` synchronously on every pointermove.** Same anti-pattern fixed for hover in `98bc609`; should rAF-coalesce.

- **F7. Atlas-build promise can resolve AFTER `rebuildForMode` already ran.** First mount: disks paint without glyphs until atlas resolves and the `.then` calls `rebuildGlyphInstanceBuffer + drawFrame` (max ~1 frame visible, usually invisible). **But** the bootstrap is `await gpu.create → setBucketPalette → fire-and-forget buildAtlas.then(…) → resizeAndFit → rebuildForMode → resizeObs.observe`. A `ResizeObserver` firing within the atlas-build window calls `resizeAndFit(false)` (sizeChanged path) which calls `rebakeNodes` → `rebakeGlyphsForMode` → `rebuildGlyphInstanceBuffer` (no-op because `local.glyphAtlas === null`) → `drawFrame` (no glyphs). The next atlas-resolve handler runs `rebuildGlyphInstanceBuffer` again and recovers. Window is small but the order is undefined.

- **F8. `rebakeNodes` rebuilds `hitNodes`/`hitById` but a concurrent `hitTestAt` (synchronous pointermove handler) can read mid-replacement.** JS is single-threaded so this only matters if `rebakeNodes` is ever called from inside a pointermove handler (it isn't today). But `camera.onChange` IS called from `panByScreen` synchronously during a pointermove, and `onChange` can call `rebakeNodes` on 5%-drift. **Pan doesn't change scale**, so today the 5%-drift never fires from pan. The moment a synthetic gesture combines pan with zoom in one handler, this could fire mid-handler. Latent.

### 🟢 POLISH

- **F9. Wheel handler calls `hitTestAt + setHoverId` synchronously on every wheel event** (forge.js:2045-2046). Rapid wheel = O(N) hit-test at wheel cadence. Should reuse the rAF-coalesced setHoverId path that pointermove already has — or skip hit-test entirely during a wheel ease (the user is zooming, not hovering).
- **F10. `rebuildForMode` wholesale-replaces `local.nodeStates`/`nodeTargets`/`edgeStates`/`edgeTargets`** with fresh `new Float32Array(…)`. This violates the animation-pipeline audit's invariant #1 but is correct here because instance counts differ across modes. Add a comment explicitly marking this as the SOLE legitimate wholesale-replace site, to prevent a future refactor from "fixing" it.
- **F11. `local._forgeDebug` is reassigned on every `render()`** with no cleanup of the prior. Console-saved refs become stale after a view-switch. Either skip reassignment when one exists (rare to keep alive across mounts) or null-out the closure-captured `local` on destroy.
- **F12. `attachInteractions()` REPLACES `local.resizeObs`** (forge.js:2056-2063). It disconnects the original observer that bootstrap created, then attaches a new wrapped one. Two observers exist during the swap window (one cycle of `requestAnimationFrame`-ish). If a resize fires DURING the swap, `resizeAndFit` may run twice for the same size — sizeChanged check makes the second one a no-op. Benign but ugly. Cleaner: pass the wrapped observer in from `bootstrap` originally.
- **F13. `local.lastSize` initialised to `{ w: 0, h: 0 }`.** First `resizeAndFit` reads a `rect` — if `stage` is `display:none` or zero-sized at mount (very early route fire), `lastSize = { w: 1, h: 1 }` (`Math.max(1, …)`). Camera then `fitToExtent` to a 1×1 viewport → tiny world, garbage state. Recovers on the next real resize. Should bail out of `resizeAndFit` if `rect.width === 0` and not fall back to `1`.
- **F14. `recomputeFocus` allocates `interleavePairs(states, selectFlags)` every call** (forge.js:1483). At 60 Hz hover that's 60 fresh typed-array allocations + a copy. Minor GC pressure; could write directly into `local.nodeTargets`.
- **F15. `glyphUvUbo` write happens once at atlas-load in `setGlyphAtlas`.** If the atlas is ever rebuilt at runtime (e.g., DPR change for retina sharpness — flagged as "not urgent" in the glyph migration handoff), the UV upload must repeat. No invariant currently enforces this; comment is needed.
- **F16. `local.params` mutations are not transactional.** A dev-panel slider drag firing 100 `setParam` calls in 100 ms triggers 100 individual `rebakeEdges` / `rebakeNodes` calls. Each is a full pack of all instances. The animation-pipeline audit history notes this for hover; same lesson for the panel. (Not in scope for this audit, but the pattern is the same.)

## 5. Invariant-enforcement proposals (HIGH LEVEL — no patches)

P1 (addresses F1, F2). **Renderer destroy must enumerate every GPU resource it creates.** Single source-of-truth list at top of `create()`: `const owned = []; const own = (o) => { owned.push(o); return o; }`; then `destroy() { for (const o of owned) try { o.destroy(); } catch {} device.destroy(); }`. Eliminates the entire class of "did we destroy X" bugs. View-side: `_engine.destroy` should symmetrically cancel EVERY rAF id it has scheduled (`animRafId`, `_hoverRafId`, `local.idleLabelRaf`, plus the per-scrubber rAF if F6 lands).

P2 (addresses F3). **`rebuildForMode` must drain pending hover state**: cancel `_hoverRafId`, clear `_hoverPendingId`, set `local.hoverId = null` (already done), then call `recomputeFocus()` AT THE END (not at the start) so the new mode's empty-hover state is the one that flows through to GPU. The current `drawFrame()` at end of `rebuildForMode` is NOT the same as `recomputeFocus` — only the latter resizes the state buffers properly. Today the state buffers are sized correctly by the explicit `local.nodeStates = new Float32Array(...)` lines, but the `focusedSet` flow is bypassed.

P3 (addresses F4). **`camera.onChange` listener must guard against firing on the trailing edge of `fitToExtent` calls it didn't trigger.** Two options:
- (a) After `camera.fitToExtent` in `rebuildForMode`, IMMEDIATELY set `local.packedAtScale = camera.state.scale` so the next listener fire sees ratio === 1.
- (b) Have `camera.fitToExtent` accept a "silent" flag that skips the emit, and use it in `rebuildForMode` (the subsequent `packNodes` call sets the scale-baked radius correctly anyway).
Option (a) is one line; option (b) is the cleaner long-term shape.

P4 (addresses F5). **`wireTimelineScrubber` must split into `wireTimelineScrubber` (DOM + event handlers, once at bootstrap) and `refreshScrubberBounds` (re-derives lo/hi + repaints UI, called from `rebuildForMode`).** Preserve `local.timeline.inDate/outDate` across modes only if they still fit within the new lo/hi; otherwise clamp.

P5 (addresses F6). **Scrubber drag must rAF-coalesce `recomputeFocus`** using the same pattern as `setHoverId`. One `_scrubRafId` + one `_pendingScrubDates` payload; rAF dispatches.

P6 (addresses F7, F8). **`rebuildForMode` and `rebakeNodes/rebakeEdges` should be ATOMIC w.r.t. observable state.** The pattern that works: (1) build everything into temporaries, (2) swap `local.mode = newMode` and state buffers in one synchronous block, (3) THEN call `drawFrame` / `recomputeFocus`. Today `rebuildForMode` does (1)–(3) inline but the state buffers are assigned BEFORE the `local.mode.nodesById` is built — a concurrent read (only possible via a pending rAF handler) sees inconsistent state. Atomicity check: the assignment block from `local.mode = { … }` through `rebuildGlyphInstanceBuffer()` must execute with no awaited promises.

P7 (addresses F9). **Wheel handler should skip hit-test until the zoom ease settles.** During `zoomAnim` the cursor's world position is changing continuously; a hit-test mid-ease is misleading anyway. Re-test on `zoomAnim === null` (animation settled) via the animation-loop's terminal frame.

P8 (addresses F10). **Document the wholesale-replace exception** with a comment at `rebuildForMode`'s `local.nodeStates = new Float32Array(...)` lines:
> "EXCEPTION to the animation-pipeline invariant #1 (no wholesale-replace) — cross-mode buffer sizes differ, so replacement is required. Do NOT factor this into a `rebake*` helper that the per-frame paths could call."

P9 (addresses F13). **`resizeAndFit` should bail (not fall back to 1×1) when `rect.width === 0`.** A zero-size stage means the view is hidden or detached; doing a `fitToExtent` to a 1×1 viewport corrupts camera state. Add `if (w < 8 || h < 8) return;` early.

P10 (addresses F12). **Hoist the wrapped `ResizeObserver` construction into `bootstrap`** so there's never two observers attached to the stage at once. The `attachInteractions` swap-the-observer dance is a hint that the bootstrap order should be: create observer, then attach interactions, then `observer.observe(stage)` — never disconnect-and-replace.

P11 (cross-cutting, addresses every order-of-ops finding above). **Add a lifecycle invariant block as a comment at the top of `forge.js`** enumerating the ORDER constraints discovered across the past four invariant-fix sessions:
1. `gpu.create` → `setBucketPalette` → `buildAtlas` (fire and forget; resolves into `setGlyphAtlas`)
2. `resizeAndFit(initial=true)` BEFORE `rebuildForMode` (so `local.lastSize` is set when fit runs)
3. Inside `rebuildForMode`: `fitToExtent` BEFORE `packNodes` (so pack reads correct scale — see F4 / pack-scale invariant)
4. `setPanBounds` AFTER `fitToExtent` (so clamp is against the new bounds, not the old)
5. `ResizeObserver.observe(stage)` AFTER initial `rebuildForMode` (so the first synthetic resize isn't fighting bootstrap state)
6. `camera.onChange` listener attached AFTER initial `rebuildForMode` (so its 5%-drift check has a valid `local.packedAtScale`)
7. `attachInteractions` LAST (so handler closures see the fully-initialized `local`)
A future agent that sees the order and the rationale won't re-introduce the bugs already fixed.
