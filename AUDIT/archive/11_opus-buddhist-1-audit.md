# Codex Atlas — post-hoc audit (opus-buddhist-1, 2026-05-14)

_Written after delivering the Buddhism wedge (30 nodes), upgrading 4 existing nodes, and wiring the Scripture-tab Buddhist canon corpus (8 sections, 14 books). This audit complements `AUDIT/00_AUDIT_OVERVIEW.md` from a hands-on-this-session perspective — what I noticed by doing, not by reading._

The previous audit found the load-bearing content gaps (Hittite/Hurrian, Apostolic Fathers, Chinese canon). I'm not going to rewrite that. This memo flags what surfaced from the inside of one batch and from one Scripture-tab wiring session that the external audit didn't (or couldn't) see.

## 1. The single largest practical issue: concurrent-agent registry contention

By the time I tried to update [ACTIVE-AGENTS.md](../00_meta/ACTIVE-AGENTS.md) with my finished-block, the file had been edited >5 times in the same minute by `opus-islam-1`, `opus-ethiopian-3`, and `opus-scripture-1`. I hit the harness's "file modified since read" guard ~6 times in a row. Same on [STATUS.md](../00_meta/STATUS.md). I ended up doing both writes with Python heredocs.

This will get worse, not better. The current convention has every agent write the SAME 2-3 registry files (ACTIVE-AGENTS, STATUS, canonical-slugs). At today's pace (5 parallel agents per session) it's already fragile. By 10 it breaks.

**Proposal:** split the registry.
- Each agent appends a `00_meta/agents/opus-<wedge>-<n>.md` file (per-agent, no contention)
- A 30-line `build_agents.py` script concatenates them into `ACTIVE-AGENTS.md` as the rendered registry view
- Same pattern for STATUS: per-batch `STATUS-fragments/2026-05-14-opus-buddhist-1.md`, rolled up by build script
- `canonical-slugs.md` is already generated by `build_dashboard.py` and doesn't need this; the issue is hand-edited files only

Cost: ~1 hour. ROI: removes the single most reliable source of frustration in the parallel-agent workflow.

## 3. The YAML-id vs file-stem dual-naming issue is a slow leak

When I created `phase-3-029-milindapanha.md`, the YAML says `id: "P3-029-milindapanha"`. Wikilinks across the vault use the file-stem form `phase-3-029-milindapanha`. The Scripture view papers over this with [`scriptureResolveBookId()`](../src/js/app.js) — an alias shim. Every other view should also be doing this implicitly, and the dashboard rebuild reports it doesn't always.

Audit-00 mentioned this. From inside a new batch I can confirm: it bites every new agent. Today's 3.9% dead-link rate is partly this; it's not all slug-drift in the genuine sense.

**Proposal:** make `derive_id()` in [build_data.py](../build_data.py) canonicalize on file-stem (drop the `P{phase}-` prefix logic). This is a single-function change. Migration: regenerate `data.js`; existing wikilinks already use the file-stem form, so the only thing that breaks is references-from-prose to `[[P5-002-heart-sutra]]` style ids — which I haven't seen anywhere.

Closes an estimated 50–100 dead-link occurrences in one Python edit.

## 6. Vault-content coverage — what hands-on work surfaced

The external audit covered the largest gaps (Hittite/Hurrian, Chinese canon, Apostolic Fathers, etc.). What I'd add from the Buddhism-wedge perspective:

### 6a. The cross-tradition reception layer is still thin in two specific places

**Buddhist → Manichaean → Cathar → modern-Western continuity.** My batch noted (in [tradition-greco-buddhism.md](../07_traditions/tradition-greco-buddhism.md) prose) that Mani borrowed the *Buddha* title for himself ("Buddha of Light"), that Sogdian-Buddhist-Manichaean translation overlap is documented (Asmussen 1965), and that the Barlaam-and-Josaphat legend is the most consequential Buddhist→Christian hagiographic transmission edge. None of these are encoded as edges. The vault has [tradition-manichaeism], [tradition-catharism], [phase-4-014-cologne-mani-codex], and the Buddhist documents. Wiring this would take ~1 hour and surface the Iran-as-Buddhist-Christian-transmission-corridor MASSIVE-win.

**Indo-Greek → Indo-Iranian frontier as a unified layer.** I created [[tradition-greco-buddhism]] but the parallel Indo-Iranian / Indo-Scythian / Kushan religious-syncretic layer (Iranian Mithra ↔ Buddhist iconography on Kushan coinage; Heliodorus pillar Vaiṣṇavism; Sogdian-Christian-Buddhist-Manichaean polyglot inscriptions) is documented in prose but isn't its own tradition node. Probably should be.

### 6b. Africa beyond Egypt + Ethiopia is the single largest geographic dark zone

Dashboard quality-issues lists Damballa, Erzulie, Oshun, Ogun, Baron Samedi, Yemoja, Pachamama as 1-ref metadata. The `afro-diasporic-syncretism` and `orisha-pantheon` and `possession-ritual` themes are 4-ref dead-links. The Yoruba pantheon proper (Olodumare, Eshu, Shango, Obatala) is half-stubbed; Akan/Vodun/Bantu/Khoisan is barely there.

For a project whose mission is "every tradition gets equal weight," sub-Saharan Africa being represented by Egypt + Ethiopia + a few stub Yoruba/Vodun deities is the gap that most contradicts the mission statement. A wedge-batch on the scale of `opus-buddhist-1` here — `opus-yoruba-vodun-1` perhaps — would close the most-mission-critical gap currently open.

### 6c. Mesoamerica / Andean / pre-Columbian Americas

Tezcatlipoca, Coatlicue, Chac, Mictlantecuhtli, Tlaloc, Tonatiuh, Inti, Pachamama all 1-ref. Popol Vuh + Codex Borgia exist as documents but the Mesoamerican pantheon and the `mesoamerican-cosmogony` theme (10 dead-link refs) are skeletal.

### 6d. Pre-Christian Northern Europe

Odin, Frigg, Freyja, Freyr, Tyr, Baldr, Hel all 1-ref. Eddas exist as documents but the deity-side is anemic and the `norse-cosmogony` / `ragnarok-apocalyptic` themes are 4-ref dead-links.

## 7. UI / feature gaps the existing audits didn't focus on

The prior audits cover content, schema, methodology. None of them critique the viewer app's investigation-tool affordances. From a hands-on perspective:

### 7a. No full-text search

`STATE.filter.search` exists in [app.js](../src/js/app.js:54) but is referenced only in narrow contexts; there's no global "find every node mentioning Pyrrho of Elis" feature. For an investigation tool, this is structural. The vault is now 1637 nodes × ~300-2000 words of body content each — that's ~2-3 million words of searchable text being displayed in a browser with no search.

**Proposal:** add a top-bar search input that runs an in-memory `.includes()` scan across `node.body` + `node.title` + `node.aka` and shows ranked results in a results pane. Cost: ~2 hours. Performance at 1637 nodes is fine for in-memory scan.

### 7b. No deep-link / URL state

Click an entity in the Scripture view, hover it to surface its cross-corpus trail-arc, screenshot. There is no URL that reproduces that state. The user cannot share what they're looking at.

`window.history.replaceState` calls: zero in app.js. This is fixable in a few hundred lines — encode `view`, `corpus` (for scripture), `selected`, `family-filter` into the URL hash, parse on load. Cost: half a day. Once in place, the audit-pattern of "go look at the Greco-Buddhist hull and tell me what you see" becomes a link instead of a 4-step manual.

### 7c. No tier-badge rendering in the detail panel

`refs[].tier` is `1`/`2`/`3`/`4` in YAML for hundreds of nodes. I have not seen it surfaced in the UI. A green-Tier-1 / yellow-Tier-2 / orange-Tier-3 / red-Tier-4 colored chip next to each citation in the detail panel would directly serve the source-integrity-discipline goal — the user can see at a glance whether a node leans on Loeb editions or Acharya S.

### 7d. No "MASSIVE-win" filter

The user's framing makes the cross-tradition tracing edges THE prize. [STATUS.md](../00_meta/STATUS.md) enumerates 10 (now ~22) such edges by number. The atlas has no way to filter to just those edges.

**Proposal:** add a `tags: [massive-win]` convention to edges (via YAML on either endpoint), and a UI toggle "Show only MASSIVE-win edges." This makes the project's literal stated payoff one click away.

### 7e. Trail-arcs in Scripture view only fire on hover

The cross-corpus entity trails (Moses across J/E/D/Quran; Avalokiteśvara across Heart-Sūtra/Lotus/Sukhāvatī; Solomon across Bible/Kebra-Nagast/Tewahedo) are the visual MASSIVE-win moment — and they only render when the user hovers an entity instance. There's no "show all cross-corpus trails" toggle.

The trails are faint-by-default-and-bright-on-hover (per the design in [opus-scripture-1's design notes](../00_meta/ACTIVE-AGENTS.md)). A keyboard-toggle to flip them ALL on at low opacity would let the user see the full graph density of the Scripture canvas at a glance.

### 7f. No "recently added" / changelog panel in the UI

The vault gains ~30-150 nodes per session. STATUS.md is the changelog but it lives outside the UI. A "what was added in the last 24 hours / 7 days / 30 days" panel — driven by file-mtimes or by parsing the STATUS.md headlines — would orient returning users.

### 7g. The screenshot quirk

When I screenshot the live preview at port 8742, the captured image is a thin vertical strip even after `preview_resize` to desktop. The DOM is fine (verified via inspection). Either the SVG viewport sizing or the preview tool's capture path has a bug. Not user-impacting for direct viewing — but if you want to publish atlas-canvas screenshots for documentation or sharing, this needs investigation.

## 9. What's working well — to keep

To balance the critique: a few things the project has gotten right that are easy to underestimate.

- **The pre-flight protocol (DASHBOARD → canonical-slugs → methodology → per-phase TODO → rebuild after) actually works.** When I followed it cold as a new agent, I produced a batch that integrated cleanly with 4 other concurrent batches and dropped the dead-link ratio. This is rare.
- **The tier-1/2/3/4 source policy + the `[claim: contested]` + `[claim: pseudoscholarship]` discipline is unusually rigorous** for a comparative-religion project. Most projects either go pure-academic (no Tier 4) or pure-everything-bagel (no tiering). The middle path here is the right one for the user's investigation-tool framing.
- **The Scripture-view abstraction (corpus registry + alias shim + auto-populated entity hulls)** is the cleanest single design decision in the app. It scales linearly with vault content.
- **The "MASSIVE-win edges" enumeration in STATUS.md headlines** does the right rhetorical job — it tells anyone reading the doc what to look for and why.
- **The honest open-gaps list at the end of every finished-block** is the second-most-important thing the project does. It means no batch ever pretends to be complete. Every wedge admits what it didn't cover.

If the project is going to scale beyond five concurrent agents and beyond the Mediterranean-Levantine-Iranian-Indic axis, the bottleneck is no longer "what content to add" — the audit already maps that — it's **viewer features** (search, deep-link, tier-badging) and **process plumbing** (registry-per-agent, file-stem-canonical ids). Content adds keep landing; the infrastructure to make that content investigatable and shareable is now the lagging edge.
